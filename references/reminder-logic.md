# 提醒能力判定逻辑与执行标准

本文件定义TA工作助手8大核心模块的**判定逻辑**（什么时候触发、怎么判断、按什么规则算）和**执行标准**（输出什么、怎么输出、质量要求），确保每次输出一致、可预期、可校验。

---

## 一、智能待办清单

### 1.1 待办类型判定逻辑

按各招聘系统的状态字段映射，统一判定为三类待办：

| 待办类型 | 判定条件 | 飞书实现 | 北森实现 | Moka实现 |
|---------|---------|---------|---------|---------|
| 待评估简历 | 投递状态=待评估/初筛中 **且** 处理人=当前用户 | 投递列表→status=待评估→handler=当前用户 | 申请列表→status=待评估→handlerId=当前用户 | 候选人列表→stage=preliminary_filter→jobManager.email=当前用户 |
| 待面试 | 面试时间>当前时间 **且** 面试官包含当前用户 | 面试列表→interviewer_ids包含当前用户→start_time>now | 面试列表→面试官包含当前用户→时间>now | 候选人列表→stage=interview→面试官包含当前用户 |
| 待写评估 | 面试已结束 **且** 评价状态=未评价 **且** 面试官=当前用户 | 面试列表→status=已面试未评价→interviewer=当前用户 | 面试列表→评价状态=未评价→面试官=当前用户 | 候选人列表→面试已完成→评估状态=未写 |

### 1.2 优先级四级判定逻辑

| 级别 | 判定条件（满足任一） | 标识 | 排序权重 |
|------|---------------------|------|---------|
| P0 最高 | 急招岗位 **且** 已超时 | 🔥🔴 | 100 |
| P1 高 | 急招岗位 **或** 已超时 **或** 内推候选人 | 🔥/🔴/⭐ | 80 |
| P2 中 | 即将超时（≤1天）**或** 匹配度≥80分 | ⚠️/💎 | 60 |
| P3 低 | 普通待办 | 无 | 40 |

**同级排序规则**：等待时长降序（等得越久越靠前）→ 创建时间升序（越早越靠前）→ 系统优先级（飞书>北森>Moka，可配置）。

### 1.3 关键标签判定逻辑

| 标签 | 判定条件 |
|------|---------|
| 🔥 急招 | 岗位标签含"急招/紧急/urgent" **或** 岗位创建<7天且headcount>0 **或** 业务方标记急招 |
| ⭐ 内推 | 来源渠道=内推/referral **或** 推荐人字段非空 |
| 💎 高匹配 | 简历与JD匹配度评分≥80（由简历初筛模块计算） |
| ⚠️ 即将超时 | 距离黄色超时阈值≤1天 |

### 1.4 多系统重复去重逻辑

- 判定：同一候选人在多系统出现（姓名+手机号匹配 **或** 姓名+邮箱匹配）
- 处理：保留最新状态的一条，标注"多系统重复"，链接指向最新状态所在系统
- 不自动删除另一条，用户可选择保留哪个系统的记录

### 1.5 任务状态变更追踪

- 每次拉取待办时，与上一次快照对比
- 新增任务：标注"NEW"
- 已完成任务：从待办列表移除，计入今日完成统计
- 积压趋势：较昨日新增X份、完成Y份、净变化Z份

### 1.6 执行标准

- ✅ 每条待办必含：候选人姓名、岗位、优先级标签、等待时长、直达链接
- ✅ 排序：P0→P1→P2→P3，同级按等待时长降序
- ✅ 顶部汇总：各类型数量 + 超时数量 + 较昨日新增/完成
- ✅ 底部建议：时间分配 + 批量处理建议（同岗位≥3份时提示）
- ✅ 多系统模式下每条标注来源系统 `[飞书]`/`[北森]`/`[Moka]`
- ✅ 所有链接域名与来源系统匹配

## 二、四种节奏定时推送

### 2.1 推送日判定逻辑

| 场景 | 默认行为 | 可配置项 |
|------|---------|---------|
| 工作日（周一至周五） | 推送 | `push_morning_days` |
| 周末（周六周日） | 不推送 | `push_weekend_enabled`（默认false） |
| 法定节假日 | 不推送 | `push_holiday_enabled`（默认false，需节假日日历数据） |
| 用户请假（飞书日历标记请假/外出） | 不推送 | `push_skip_when_leave`（默认true） |

### 2.2 推送内容动态判定逻辑

| 推送节奏 | 触发条件 | 无数据时行为 |
|---------|---------|------------|
| 早间9:00 | 每个推送日固定推送 | 推"今日无待办，可专注其他工作"，不跳过 |
| 午间13:30 | 下午有面试 **或** 上午有未完成待办 | 跳过本次，不打扰用户 |
| 下班17:30 | 每个工作日固定推送 | 推"今日全部完成，辛苦了"，不跳过 |
| 周五16:00 | 仅周五推送 | 推周度汇总 |

### 2.3 推送静默判定逻辑

| 触发 | 静默范围 | 恢复方式 |
|------|---------|---------|
| 用户说"今天不要推/暂停推送/勿扰" | 当天剩余所有推送 | 次日自动恢复，或用户说"恢复推送" |
| 用户说"暂停一周/暂停X天" | 指定天数内所有推送 | 到期自动恢复 |
| 用户说"取消定时推送" | 永久取消所有定时推送 | 用户重新配置 |
| 推送时间用户在会议中（日历判断） | 本次推送延迟到会议结束后 | 自动恢复 |

### 2.4 推送去重逻辑

- 用户在推送前30分钟内已手动查询相同内容 → 简化推送（只推新增/变化部分，不重复全量）
- 判断依据：查询内容类型（待办/面试/报表）+ 时间窗口

### 2.5 推送失败处理逻辑

1. 推送失败自动重试2次（间隔1分钟、3分钟，指数退避）
2. 仍失败 → 记录日志，标记为"推送失败"
3. 用户下次主动查询时 → 提示"今早的推送失败了，现在为你补上"并输出内容
4. 连续3天推送失败 → 提醒用户检查推送渠道配置

### 2.6 执行标准

- ✅ 推送时间误差≤1分钟
- ✅ 开头问候："早上好，今天是X月X日周X"
- ✅ 结尾快捷操作："回复'待办'查看详情 / 回复'暂停'今天不再推送"
- ✅ 所有任务带链接，格式与手动查询一致
- ✅ 推送内容模块与配置的 `push_*_modules` 一致
- ✅ 多系统模式下来源标注正确

## 三、黄红两级超时预警

### 3.1 超时起算时间判定逻辑

| 任务类型 | 起算点 |
|---------|--------|
| 待评估简历 | 投递状态变为"待评估"且分配给当前用户的时间 |
| 待写面试评估 | 面试结束时间 |
| 面试准备 | 面试安排时间（面试前1天未查看简历算准备超时） |

### 3.2 分级超时阈值（默认值，全部可配置）

| 任务类型 | 🔵 即将超时 | 🟡 黄色预警 | 🔴 红色预警 | 配置项 |
|---------|-----------|-----------|-----------|--------|
| 待评估简历 | 距3天≤1天 | ≥3天 | ≥7天 | `timeout_warning_days` / `timeout_critical_days` |
| 待写面试评估 | 距2天≤1天 | ≥2天 | ≥5天 | `interview_eval_warning_days` / `interview_eval_critical_days` |
| 面试准备 | 面试前1天 | 面试当天未查看 | — | `interview_prep_warning_ahead_hours` |

### 3.3 工作日计算逻辑

- 默认：按自然日计算（含周末和节假日）
- 可配置 `timeout_calc_workdays_only=true`：仅工作日计算，周末和法定节假日不计入超时天数
- 节假日数据来源：内置法定节假日日历，可逐年更新

### 3.4 超时趋势判定逻辑

| 趋势 | 判定条件 | 提示 |
|------|---------|------|
| 超时增加 | 本周超时数较上周增加>20% | "本周超时任务较上周增加X份，注意工作节奏" |
| 超时减少 | 本周超时数较上周减少>20% | "本周超时任务减少X份，继续保持" |
| 岗位集中 | 某岗位超时≥5份 | "XX岗位简历积压严重，建议与业务方沟通筛选标准或增加面试官" |

### 3.5 执行标准

- ✅ 超时任务标注精确时长（如"已超时3.5天"）
- ✅ 红色超时排最前，醒目标识 🔴
- ✅ 黄色超时其次 🟡
- ✅ 即将超时标注 🔵
- ✅ 超时≥5份时给出批量处理建议（按岗位/类型分组）
- ✅ 每周汇总含超时趋势对比
- ✅ 每条超时任务带直达链接
- ✅ 超时天数计算与配置的计算方式一致（自然日/工作日）

## 四、简历摘要与横向对比

### 4.1 简历摘要字段标准

| 级别 | 字段 | 说明 |
|------|------|------|
| P0 必含 | 姓名、应聘岗位、最高学历、毕业院校、专业、工作年限、最近公司、最近职位、核心技能标签(3-5个)、直达链接 | 缺一不可，缺失时标注"暂无" |
| P1 可选 | 年龄、所在地、薪资期望、来源渠道、简历更新时间 | 有则展示，无则省略 |

### 4.2 亮点判定逻辑

满足以下任一条件即标记为亮点，**最多列3条，按重要性排序**：

| 亮点类型 | 判定条件 |
|---------|---------|
| 学历背景 | 985/211/QS前100院校 |
| 公司背景 | 大厂/行业知名公司工作经历 |
| 经验匹配 | 工作年限与岗位要求匹配度≥80% |
| 技能匹配 | 核心技能覆盖岗位要求≥80% |
| 稳定性 | 最近一份工作≥2年 |
| 成长速度 | 晋升速度快（如2年内从初级到高级） |
| 特殊优势 | 有行业证书、开源项目、专利等 |

### 4.3 风险点判定逻辑

满足以下任一条件即标记为风险点，**最多列3条，按严重程度排序**：

| 风险类型 | 判定条件 |
|---------|---------|
| 频繁跳槽 | 最近3年内换工作≥3次 |
| 职业gap | 有≥6个月的职业空白期且无合理解释 |
| 经验不匹配 | 工作年限与岗位要求差距>30% |
| 技能不匹配 | 核心技能覆盖岗位要求<50% |
| 学历不达标 | 低于岗位最低学历要求 |
| 简历异常 | 信息前后矛盾、时间线对不上 |
| 薪资差距 | 期望薪资超出岗位预算>30% |

### 4.4 匹配度评分算法（百分制）

| 维度 | 权重 | 评分依据 |
|------|------|---------|
| 硬性条件 | 40分 | 学历10分 + 工作年限10分 + 专业相关度10分 + 所在地10分 |
| 经验匹配 | 30分 | 相关行业经验15分 + 相关岗位经验15分 |
| 技能匹配 | 20分 | 必备技能15分 + 加分技能5分 |
| 软性条件 | 10分 | 稳定性5分 + 成长潜力5分 |

**结论判定**：
- ≥80分 → 推荐通过
- 60-79分 → 待定
- <60分 → 不推荐

### 4.5 横向对比维度选择逻辑

| 岗位类型 | 对比维度 |
|---------|---------|
| 默认所有岗位 | 学历、工作年限、最近公司、核心技能、匹配度、亮点、风险点 |
| 技术岗追加 | 技术栈、项目经验 |
| 产品岗追加 | 产品类型、用户规模 |
| 设计岗追加 | 作品集、设计风格 |
| 运营岗追加 | 运营数据、渠道经验 |

- 对比候选人≥3人时，增加"推荐排序"列
- 对比维度可由用户自定义指定

### 4.6 执行标准

- ✅ 单份简历摘要≤200字（核心信息卡形式）
- ✅ 亮点和风险点各最多3条，按重要性排序
- ✅ 匹配度评分必须展示各维度得分，不能只给总分
- ✅ 横向对比用表格形式（候选人做列，维度做行）
- ✅ 敏感信息（手机号、身份证号）默认脱敏展示
- ✅ 简历信息不完整时标注"简历信息不完整，以下为已有信息"
- ✅ 样本量<5份时不做统计性结论
- ✅ 每位候选人附直达链接

## 五、面试准备包与纪要整理

### 5.1 面试准备包触发逻辑

| 触发方式 | 时机 | 说明 |
|---------|------|------|
| 主动触发 | 用户说"帮我准备面试" | 立即生成 |
| 定时触发 | 面试前30分钟 | 需开启事件驱动提醒 `event_reminder_enabled=true` |
| 提前提醒 | 面试前1天 | 仅急招/高阶岗位（岗位级别≥P7或headcount=1） |

### 5.2 准备包按面试轮次区分内容

| 内容模块 | 一面（初面） | 二面（复面） | 终面 |
|---------|------------|------------|------|
| 候选人背景摘要 | ✅ 详细 | ✅ 精简 | ✅ 极简 |
| 简历疑点验证 | ✅ 重点 | ✅ 参考 | ❌ |
| 基础能力提问 | ✅ 5-8个 | ❌ | ❌ |
| 专业深度提问 | ✅ | ✅ 重点3-5个 | ❌ |
| 上一轮反馈+待验证点 | ❌ | ✅ 重点 | ✅ 参考 |
| 团队/文化匹配提问 | ❌ | ✅ | ✅ 重点2-3个 |
| 薪资/期望沟通 | ❌ | ❌ | ✅ |
| 推荐问题总数 | 5-8个 | 3-5个 | 2-3个 |

### 5.3 提问方向生成逻辑

按以下优先级生成问题，总数控制在推荐范围内：

1. **JD核心能力要求** → 每个能力要求对应1-2个问题
2. **简历风险点** → 每个风险点对应1个验证问题
3. **上一轮待验证点** → 每个待验证点对应1个深入问题
4. **候选人背景亮点** → 准备1-2个深挖问题

**问题类型分布**：行为面试题（STAR法则）60% + 专业技术题30% + 开放性问题10%

### 5.4 面试纪要整理触发逻辑

| 触发方式 | 时机 |
|---------|------|
| 主动触发 | 用户说"帮我整理纪要/写评估" |
| 定时提醒 | 面试结束2小时后用户仍未写评估 → 提醒并提供纪要草稿 |
| 输入来源 | 用户提供的面试速记/录音转写/手写笔记 |

### 5.5 纪要必含模块（P0，缺一不可）

1. **基本信息**：候选人姓名、应聘岗位、面试轮次、面试时间
2. **能力评估表**：按岗位核心能力维度打分（1-5分）+ 评语
3. **优势**：≤3条，每条有具体事例支撑
4. **风险点/待验证点**：≤3条
5. **综合结论**：推荐通过/待定/不推荐 + 核心理由
6. **下一步建议**：进入下一轮/加面/拒绝/发offer

**可选模块（P1）**：面试问答记录、薪资沟通记录、面试官个人感受。

### 5.6 评估结论判定逻辑

| 结论 | 判定条件 |
|------|---------|
| 推荐通过 | 核心能力全部≥4分/5分，无重大风险点，优势突出 |
| 待定 | 核心能力基本达标（3-4分），有风险点但可接受，或有亮点也有明显短板 |
| 不推荐 | 核心能力有明显短板（<3分），或有重大风险点（诚信问题、价值观不符等） |

### 5.7 多轮面试一致性校验逻辑

| 异常情况 | 处理方式 |
|---------|---------|
| 上一轮推荐通过，本轮不推荐 | 提醒"与上一轮结论不一致，请确认是否有新的考量" |
| 同一能力维度多轮打分差>2分 | 提醒"该能力维度评价差异较大，建议综合判断" |
| 多轮结论均为待定 | 建议"多轮评价均为待定，建议加面或明确决策标准" |

### 5.8 执行标准

- ✅ 面试准备包控制在一页内（可快速浏览），重点问题加粗
- ✅ 提问要具体可执行，不能是"问问项目经验"这种空话，要给出具体问题
- ✅ 面试纪要结构清晰，用标题分段
- ✅ 能力评估用表格形式（维度、打分、评语）
- ✅ 结论必须明确，不能模棱两可
- ✅ 纪要末尾附评估提交链接
- ✅ 多轮面试时附带上一轮结论摘要

## 六、工作量与效率趋势

### 6.1 统计周期判定逻辑

| 周期类型 | 界定 | 触发 |
|---------|------|------|
| 自然周 | 周一00:00至周日23:59 | 默认周报 |
| 自然月 | 每月1日至月末 | 默认月报 |
| 自定义 | 用户指定（如"最近7天""上个月""Q3"） | 用户主动查询 |

- 所有时间按用户所在时区UTC+8计算
- 周期边界数据以任务完成时间为准（不是创建时间）

### 6.2 工作量量化标准

统一换算为"工作量点数"，便于横向对比：

| 任务类型 | 点数 | 说明 |
|---------|------|------|
| 评估1份简历 | 1点 | 标准简历评估 |
| 参加1场面试 | 2点 | 含面试前准备+面试+面试后整理 |
| 写1份面试评估 | 1点 | 标准评估撰写 |
| 1次沟通（约面/反馈/offer） | 0.5点 | 单次沟通 |

**日工作量参考标准**：
- 5-8点：正常
- >10点：超负荷
- <3点：低负荷

### 6.3 效率指标定义与计算公式

| 指标 | 计算公式 | 单位 |
|------|---------|------|
| 简历平均处理时长 | Σ(评估完成时间 - 进入待评估时间) / 评估数量 | 天/小时 |
| 面试评估平均出稿时长 | Σ(评估提交时间 - 面试结束时间) / 评估数量 | 小时 |
| 简历处理及时率 | 3天内完成评估的简历数 / 总评估数 | 百分比 |
| 面试评估及时率 | 2天内完成评估的面试数 / 总面试数 | 百分比 |
| 日均处理量 | 周期内总工作量点数 / 工作日数 | 点/天 |
| 面试通过率 | 通过面试人数 / 总面试人数 | 百分比 |
| 简历初筛通过率 | 通过初筛人数 / 总评估人数 | 百分比 |

### 6.4 趋势对比基准

| 报表类型 | 对比基准 |
|---------|---------|
| 周报 | 与上一周对比（环比） |
| 月报 | 与上一月对比（环比）+ 与去年同期对比（同比，有数据时） |
| 自定义周期 | 与上一等长周期对比 |

**对比维度**：工作量总量、各类型占比、效率指标、超时率、通过率。

### 6.5 异常值处理逻辑

- 计算平均值时，排除超过3倍标准差的异常值（如某份简历处理了30天）
- 异常值单独标注说明，不纳入平均值计算，但纳入总量统计
- 异常值占比>10%时，提醒"数据异常值较多，平均值可能失真，建议查看中位数"

### 6.6 工作饱和度判定逻辑

| 饱和度 | 判定条件（满足任一） | 建议 |
|--------|---------------------|------|
| 超负荷 | 日均工作量>10点 **或** 待办积压>15份 **或** 超时率>30% | 给减负建议：哪些可延期、哪些可转交、哪些可与业务方沟通降低标准 |
| 正常 | 日均5-8点，待办5-10份，超时率<15% | 肯定当前节奏，给微调建议 |
| 低负荷 | 日均<3点，待办<3份 | 提醒"当前工作量较低，可利用时间做经验沉淀/复盘" |

### 6.7 效率改进建议生成逻辑

| 问题 | 判定条件 | 建议 |
|------|---------|------|
| 简历处理不及时 | 简历及时率<70% | "建议每天固定时段集中处理简历，如每天上午10点" |
| 评估出稿慢 | 面试评估出稿平均>24小时 | "建议面试结束后立即写评估，趁记忆清晰，可先用语音速记" |
| 岗位积压 | 某岗位超时≥5份 | "XX岗位简历积压严重，建议与业务方沟通筛选标准或增加面试官" |
| 周中工作量不均 | 某天工作量是其他天的2倍以上 | "周X工作量最大，建议提前预留时间或提前处理" |
| 通过率异常低 | 某岗位面试通过率<20% | "XX岗位面试通过率偏低，建议检查筛选标准是否过松或JD描述是否准确" |

### 6.8 执行标准

- ✅ 统计报表必含：总量数据 + 各类型分布 + 效率指标 + 趋势对比 + 结论建议
- ✅ 趋势对比用箭头标识（↑上升/↓下降/→持平）+ 百分比
- ✅ 数据用表格+文字说明结合
- ✅ 关键指标异常时用颜色标识（红/黄）
- ✅ 多系统模式下增加"按系统分布"模块
- ✅ 所有数据标注统计周期和数据来源
- ✅ 异常值处理方式透明说明

## 七、候选人画像

### 7.1 画像维度定义

| 维度 | 分类标准 |
|------|---------|
| 学历 | 博士/硕士/本科/大专及以下 |
| 院校层次 | 985/211/QS前100/普通本科/其他 |
| 工作年限 | 应届/1-3年/3-5年/5-10年/10年以上 |
| 公司背景 | 大厂/行业知名/普通公司/创业公司/其他 |
| 来源渠道 | 内推/猎头/官网投递/招聘平台/校招/其他 |
| 所在地 | 一线城市/新一线/二线/其他/海外 |
| 薪资期望 | 低于预算/预算内/高于预算 |

**默认不展示的维度**（隐私保护，用户明确要求才展示）：年龄、性别。

### 7.2 画像数据范围判定逻辑

| 范围 | 判定 | 触发 |
|------|------|------|
| 默认 | 当前所有在招岗位的候选人（含各阶段） | 无指定范围时 |
| 按岗位 | 指定岗位的候选人 | "帮我看看前端岗位的候选人画像" |
| 按阶段 | 指定阶段的候选人（如通过初筛的） | "通过初筛的候选人画像" |
| 按时间 | 指定时间范围内新增的候选人 | "本月新增候选人画像" |

### 7.3 岗位人才画像 vs 候选人画像对比逻辑

- **岗位人才画像（目标）**：从JD自动提取的理想候选人特征（学历要求、经验要求、技能要求、薪资范围等）
- **候选人画像（实际）**：实际投递候选人的特征分布
- **对比方式**：每个维度展示"目标要求 vs 实际分布"双列
- **差距判定**：实际满足目标要求的比例<80%时，标记为差距项
- **差距建议**：差距>20%时给出可执行建议，如"XX岗位3-5年经验候选人仅40%，建议拓宽招聘渠道或调整经验要求"

### 7.4 画像与招聘效果关联逻辑

需要历史数据积累（≥3个月数据）后启用：

| 分析维度 | 计算方式 | 用途 |
|---------|---------|------|
| 各维度通过率 | 各分类中通过面试的比例 | 识别哪些特征的候选人通过率高 |
| 各来源渠道入职率 | 各渠道中最终入职的比例 | 优化招聘渠道投入 |
| 各维度留任率 | 各分类中入职6个月仍在职的比例 | 识别高质量候选人特征 |
| 高质量特征组合 | 通过率+留任率双高的特征组合 | 指导筛选标准优化 |

### 7.5 画像异常识别逻辑

| 异常 | 判定条件 | 提醒 |
|------|---------|------|
| 渠道突变 | 某来源渠道占比环比变化>20% | "本月内推占比从30%降到10%，内推渠道是否出了问题？" |
| 学历断层 | 某岗位某学历层次候选人=0 | "XX岗位没有硕士学历候选人，是否需要拓宽渠道？" |
| 薪资不匹配 | >50%候选人期望薪资超预算 | "XX岗位超60%候选人期望薪资超预算，建议调整薪资范围或JD描述" |
| 来源单一 | 某岗位>70%候选人来自单一渠道 | "XX岗位候选人来源过于集中，建议拓展其他渠道降低风险" |

### 7.6 执行标准

- ✅ 候选人画像用图表+表格结合展示
- ✅ 每个维度展示分布百分比和Top3
- ✅ 岗位画像对比时用"目标 vs 实际"双列展示
- ✅ 数据量<10份时标注"样本量较小，仅供参考"
- ✅ 画像分析末尾给出1-3条可执行建议
- ✅ 年龄/性别默认不展示，用户明确要求时才展示
- ✅ 所有数据标注数据范围和统计时间

## 八、经验库沉淀

### 8.1 沉淀触发逻辑

| 触发方式 | 时机 | 默认行为 |
|---------|------|---------|
| 自动沉淀-面试 | 面试结束提交评估时 | 自动沉淀到面试经验库（可关闭 `auto_store_interview=false`） |
| 自动沉淀-筛选标准 | 简历评估做出通过/不通过决策时 | 自动更新该岗位的筛选标准和典型案例 |
| 主动沉淀 | 用户说"把这个案例存到经验库" | 立即沉淀 |
| 批量沉淀 | 周度复盘时 | 批量沉淀本周典型案例（用户确认后） |

### 8.2 面试经验库字段标准

| 字段 | 必填 | 说明 |
|------|------|------|
| 候选人ID | ✅ | 脱敏存储，不存姓名手机号 |
| 应聘岗位 | ✅ | 岗位名称和ID |
| 面试轮次 | ✅ | 一面/二面/终面 |
| 面试时间 | ✅ | 用于时间检索 |
| 候选人背景标签 | ✅ | 学历、年限、公司背景等标签 |
| 问过的关键问题 | ✅ | 3-5个关键问题 |
| 候选人回答要点 | 可选 | 简要记录 |
| 评估结论 | ✅ | 通过/待定/不推荐 |
| 核心理由 | ✅ | 1-3条关键理由 |
| 能力评分 | 可选 | 各维度打分 |
| 事后验证状态 | 自动 | 待验证/已入职/已拒绝/已离职 |
| 事后验证备注 | 可选 | 入职后表现、离职原因等 |
| 来源系统 | ✅ | 飞书/北森/Moka |
| 沉淀时间 | 自动 | 记录创建时间 |

### 8.3 评估标准库字段标准

| 字段 | 必填 | 说明 |
|------|------|------|
| 岗位名称 | ✅ | |
| 岗位ID | ✅ | |
| 筛选标准 | ✅ | 硬性条件+加分项+减分项 |
| 通过典型案例 | 可选 | 候选人背景标签+通过理由 |
| 不通过典型案例 | 可选 | 候选人背景标签+不通过理由 |
| 岗位人才画像 | 可选 | 理想候选人特征 |
| 创建时间 | 自动 | |
| 最后更新时间 | 自动 | |
| 使用次数 | 自动 | 被引用次数 |

### 8.4 数据质量校验逻辑

| 校验项 | 判定 | 处理 |
|--------|------|------|
| 必填字段缺失 | 任一必填字段为空 | 提示用户补充，或标注"信息不完整"后沉淀 |
| 结论与理由矛盾 | 结论"不推荐"但理由全是优点（或反之） | 提醒确认，用户确认后再沉淀 |
| 重复案例 | 同一候选人ID+同一轮次已存在 | 不重复沉淀，提示"该案例已存在" |
| 敏感信息检测 | 内容中包含手机号/身份证号格式 | 自动脱敏后沉淀 |

### 8.5 经验库检索逻辑

| 环节 | 规则 |
|------|------|
| 主检索维度 | 岗位名称（精确匹配+模糊匹配） |
| 辅助过滤 | 候选人背景标签（学历、年限、公司）、面试轮次、结论 |
| 排序 | 相关度（岗位匹配+背景匹配）> 时间近 > 使用次数多 |
| 返回数量 | 最多5条相关案例 |
| 检索时机 | 面试准备时自动检索、简历初筛时自动检索、用户主动查询 |

### 8.6 经验库使用场景

| 场景 | 使用方式 |
|------|---------|
| 面试准备 | 自动检索同岗位、同背景候选人的历史面试问题和结论，作为参考附在准备包中 |
| 简历初筛 | 自动检索同岗位的筛选标准和典型案例，辅助匹配度判断 |
| 评估标准迭代 | 参考历史通过/不通过案例，优化当前岗位的筛选标准 |
| 主动查询 | 用户说"看看我之前面过的类似候选人" → 检索并展示 |

### 8.7 事后验证更新机制

| 事件 | 更新内容 |
|------|---------|
| 发offer | 验证状态更新为"已发offer" |
| 候选人入职 | 验证状态更新为"已入职"，记录入职时间 |
| 入职3个月 | 提醒用户补充"入职后表现"验证（自动推送提醒） |
| 候选人离职 | 记录离职时间和离职原因，验证状态更新为"已离职"，用于回溯评估准确性 |
| 候选人拒绝offer | 验证状态更新为"已拒绝"，记录拒绝原因（如有） |

### 8.8 隐私保护规则

- ✅ 不存储候选人姓名、手机号、邮箱、身份证号等个人敏感信息
- ✅ 用候选人ID+岗位标识作为唯一键
- ✅ 经验库仅存储在用户个人空间（飞书多维表格），其他人不可见
- ✅ 用户可随时删除任何沉淀记录
- ✅ 数据保留期限可配置（默认2年，超期自动清理）
- ✅ 调用经验库时，历史案例展示自动脱敏

### 8.9 执行标准

- ✅ 沉淀操作对用户透明，面试结束后自动沉淀，无需用户手动操作
- ✅ 经验库调用时明确标注"参考历史案例"，不直接替代用户判断
- ✅ 历史案例展示时脱敏处理，不暴露候选人个人信息
- ✅ 定期（每月）提醒用户回顾和更新经验库
- ✅ 经验库数据量>50条后，提供"个人面试风格分析"和"评估准确性分析"
- ✅ 数据质量校验不通过时，不静默丢弃，明确告知用户
